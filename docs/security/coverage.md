# Input-to-server coverage and review matrix

## How to read this matrix

The companion [API register](api-coverage.md) has one row per literal or finitely resolved production-import-reachable route, including explicit inputs, guards, direct tables and delegated destinations. [UI register](ui-coverage.md) includes native and component controls, rich editors, paste/drop handlers, URL parameters, local storage, background synchronisation and exported HTML. [Machine register](input-inventory.json) retains each route's validation conditions and helper calls, middleware mounts and individual SQL sink expressions.

These are source inventories, not penetration-test certificates. A shipped import is potential reachability, not proof that a particular feature is enabled. Every route and UI row maps to the families below by its source file and, where specified, path. Empty direct-table lists require following the listed helpers; they are not evidence of a non-database route. No unexecuted endpoint or UI flow is labelled safe. Endpoint fixture tests exercise actual Drizzle queries but sometimes inject the identity boundary; only the separate built-browser test is evidence of real sign-in and session enforcement.

All API rows inherit the applicable `app.ts` mounts: CORS Origin check, cookie parsing, JSON/urlencoded 12 MB limits, optional Replit identity, platform session resolution and general rate limit. The raw Stripe webhook is mounted before body parsing and the general API limiter. `routes/index.ts` additionally mounts role-based subtree guards, entitlement middleware and routes. Per-route conditions in the JSON are combined with these mounts, not substituted for them.

The SQL register includes tagged templates, raw/identifier/query/execute calls and ORM mutators. It can count the same SQL statement at a tagged template and its enclosing execute call. This is a call-site inventory, not a count of unique database statements. Tagged values and ORM comparisons are parameterised; nested SQL fragments remain structural and were traced separately. Static Drizzle schema objects provide column/table identities. See [database review](database-evidence.md).

No route/module from the generated API register is omitted from this family mapping. No evidence found that `PressReleasePage.tsx` is imported into the production web graph. Its legacy raw HTML sink is therefore excluded as a confirmed production XSS finding. Development mockup sandbox is excluded. Development schema setup and operational scripts are inventoried where relevant to SQL but are not public forms.

## Explicit remaining coverage gaps

- AST extraction resolves string constants, the legacy-recovery conditional loop and GEO factory parameters from literal call sites; unresolved route expressions fail the generator. It still cannot certify runtime plugin registration or external package internals. Manual reconciliation found no additional application router.
- UI inventories include inactive component imports. They do not prove a screen is enabled or that every field was clicked. Frontend validation never substitutes for the server review.
- Tested punctuation/data probes are bounded representative classes, not every encoding, Unicode normalisation, field/path combination or PostgreSQL locale/version.
- Real provider OAuth/MFA recovery, external network/DNS behaviour, object-storage grants, deployed HTTPS cookies/headers, proxy header rewriting, shared rate-limit state, webhooks and paid quotas are deployment-dependent and untested.
- Concurrent project reassignment versus all subordinate writes, distributed quota races and every member-role/tenant combination have not been exhaustively tested.
- Existing fixture mocks are explicitly documented in the technical report. A route returning a denial is not evidence that its authorised write branch was exercised.
