Staging Environment Setup
🔒
Live demo is frozen. No structural changes to the live environment until cutover. Everything in tasks #381–384 happens on staging only.
Why this comes first

All of the login, SSO, permissions, and Stripe work in the tasks below must be built and tested without touching the live demo - active demo users must not be affected. A staging environment gives us a safe, isolated copy of the platform where every change can be validated before it reaches real clients.

Done looks like
  • ✓A separate deployment exists at a staging subdomain (staging.aiofusion.ai)
  • ✓Staging has its own PostgreSQL database - completely separate from production
  • ✓Staging has its own environment variables; no secrets are shared with live
  • ✓A seed script populates staging with test accounts: admin, agency/partner, and client roles
  • ✓Google OAuth redirect URIs updated so Google SSO works on staging without affecting live
  • ✓Smoke test passes: login, Google SSO, and project loading all work on staging
  • ✓Live demo confirmed unaffected
Steps
  1. 1
    Fork the project into a new Replit app - duplicate the monorepo into a separate Replit project configured to deploy to the staging subdomain; own Replit Secrets section, no shared values.
  2. 2
    Provision a separate database - create a new PostgreSQL database for staging, run all migrations against it, confirm the connection string is staging-only.
  3. 3
    Wire staging environment variables - set all required secrets (auth keys, Google OAuth redirect URIs pointing to staging URL) in the staging app.
  4. 4
    Update Google OAuth config - add staging domain as an authorised redirect URI in Google Cloud Console; leave live config untouched.
  5. 5
    Write and run a seed script - repeatable script that creates: one admin account, one Agency/Partner account with two client sub-accounts, and a sample project per client.
  6. 6
    Smoke-test - verify login, Google SSO, and project loading all work on staging before declaring it ready.
Out of scope
✕ Login or SSO changes (task #382) ✕ Stripe or billing (task #384) ✕ Migrating real user data to staging

Security & compliance highlights
  • ✓Session revocation is immediate - a removed or suspended user cannot survive on an existing session. A session_version counter per user ensures stale sessions are rejected at the next request.
  • ✓MFA mandatory for master accounts (TOTP); strongly prompted for Agency/Partner Admins; available to all users.
  • ✓Impersonation guardrails - every impersonation session is logged (who, which account, start/end). Blocked actions while impersonating: change account password/email, delete account.
  • ✓Data retention: hard-delete has 30-day recovery window; financial records retained 6 years (HMRC). GDPR erasure requests use the same pipeline.
  • ✓Rate limiting on all auth endpoints with progressive lockout after 5 failed attempts.
  • ✓Password reset: identical response whether email exists or not (no enumeration). Single-use links, 1-hour expiry.

Project-Level Access Control within Agency Accounts
💡
This task is merged into #382 and will be built as part of that sprint. It is documented separately here because it is the most granular layer of the permissions model - an Agency/Partner might have five staff members but only want two of them to access a particular client's data.
How it works
  • ✓An Agency/Partner admin can assign a staff member access to specific client projects - not all projects by default
  • ✓A staff member who logs in sees only the projects they have been explicitly granted access to
  • ✓The project switcher and sidebar reflect server-enforced visibility - no client-side filtering
  • ✓A client account sees only its own projects - never sibling clients under the same Agency/Partner
  • ✓A "Manage access" view in the Agency/Partner admin dashboard shows which staff member has access to which projects, with add/remove controls
  • ✓All permission checks are server-enforced; privilege escalation between sibling clients is not possible
Implementation approach
  1. 1
    Extend the permission model - add a project_grants join table linking a user to a specific project with a role; server logic enforces project-level grants on top of the account hierarchy.
  2. 2
    Build "Manage access" UI - agency admin dashboard view listing all staff and their project access; toggles to grant/remove access per project; changes saved immediately.
  3. 3
    Enforce visibility in project list and sidebar - update the project switcher to show only server-approved projects for the logged-in user.
  4. 4
    Guard all project routes - every API route that returns project data checks the requester's project-level grant; returns 403 for unauthorised attempts.
  5. 5
    Test role matrix on staging - test all combinations: agency admin (all), staff member (subset), client user (own only), master admin (all via impersonation).

Stripe Payments, Project Tiers & Self-Serve Billing
⚠
All Stripe work uses test-mode API keys on staging. No real money is processed until the go-live cutover in task #385.
Beta tester & VIP discount management

The master admin can invite beta testers, early adopters, and VIP accounts at a variable discount. The discount is set per invite, applied automatically at Stripe Checkout, and persists on every renewal for the lifetime of the subscription - the recipient never has to enter a code.

How it works

  1. 1
    Master admin creates a discount invite - in the master admin panel, enter the invitee's email, choose their account type (In-House or Agency/Partner), and set the discount percentage (e.g. 30%). A unique, single-use invite link is generated.
  2. 2
    Invite link sent to the recipient - the link is pre-loaded with the account type and discount level. The recipient completes the normal signup flow (email/SSO, company details, billing frequency choice).
  3. 3
    Stripe coupon applied at checkout - when the invite link is redeemed, the server creates a Stripe coupon for the specified % off (or reuses an existing one with the same value) and attaches it to the Checkout session. The discounted price is shown transparently on the Stripe Checkout page.
  4. 4
    Discount persists on renewal - the coupon is applied at subscription level (not one-time), so every quarterly or annual renewal is charged at the discounted rate automatically.
  5. 5
    Discount visible in admin subscription view - all discounted accounts are flagged in the master admin subscription table with the discount %, invite label (e.g. "Beta", "VIP"), and the date the invite was redeemed.

Rules & guardrails

  • ✓Master admin only - no Agency/Partner or other account type can create discount invites
  • ✓Variable discount - any integer % from 1-100 (100% = fully free; use the existing free-access flag instead)
  • ✓Single-use links - each invite link can only be redeemed once; unused links expire after 30 days
  • ✓Invite label - master admin sets a label at creation time (e.g. "Beta", "Early Adopter", "VIP", "Partner Preview") stored on the account record for internal reference
  • ✓Discount cannot be self-applied - a regular organic signup cannot access the discounted price; the coupon is only attached server-side when a valid invite token is present
  • ✓Discount can be removed - master admin can end the discount at next renewal via Stripe (does not affect the current billing period)
ℹ
Stripe coupon creation is handled server-side using the Stripe API at the point of checkout session creation - no coupon codes are exposed to the client. The invite token in the URL is a short-lived server-side reference, not the Stripe coupon ID.

Staging-to-Live Cutover, Account Migration & Stripe Go-Live
🚀
Cutover is performed out of hours. A database snapshot is taken immediately before the migration step. A rollback procedure is documented and tested before cutover night begins.
Done looks like
  • ✓All staging changes are deployed to the live environment
  • ✓Existing demo/beta accounts are migrated to the new auth model with no data loss
  • ✓Google and Microsoft SSO redirect URIs updated to point to the live domain
  • ✓Stripe switches from test mode to live mode
  • ✓Existing demo users can log in on the first attempt after cutover
  • ✓Rollback plan documented and tested before cutover begins
Cutover steps
  1. 1
    Pre-cutover checklist - document every environment variable, OAuth redirect URI, and Stripe config that differs between staging and live. Review with Spencer before cutover night.
  2. 2
    Take a database snapshot - captured immediately before any migration step runs.
  3. 3
    Run account migration script on live DB - execute the auth model migration against the production database; verify row counts before and after.
  4. 4
    Update OAuth providers for live - add live domain as authorised redirect URI in Google Cloud Console and Azure AD (Microsoft Entra ID); remove staging-only test URIs.
  5. 5
    Switch Stripe to live mode - replace staging test-mode API keys with live-mode keys; update webhook endpoint to live URL; confirm first live webhook event is received.
  6. 6
    Smoke-test live environment - email login, Google SSO, Microsoft SSO, project load, Stripe checkout. All must pass before declaring cutover complete.
  7. 7
    Monitor for 30 minutes - watch error logs post-cutover; rollback procedure ready if needed.
Out of scope
✕ New feature development (cutover only) ✕ Pricing changes after launch
